# Спецификация: Знания проекта — RAG-индексация и поиск

Владелец контекста: `Project Knowledge` (см. [architecture.md](../../docs/architecture.md)). Статус: черновик.

## Цель

Пакет `services/knowledge` — TypeScript-библиотека (без HTTP-сервера) плюс CLI-команды: **индексация** репозитория в **фрагменты знаний** с эмбеддингами локальной моделью qwen3-embedding через Ollama (ADR-0005) и поиск top-k по запросу. Хранилище — файловая БД на sqlite-vec. Потребители библиотеки: mcp-server (MCP-инструмент `search_project_docs`, [спека 002](../002-mcp-server/)), backend Помощника (/help) (спека 004) и review-CLI (спека 005). CLI нужен для ручного запуска и отладки (`pnpm rag:index`, `pnpm rag:query`) и как fallback на self-hosted runner (ADR-0006).

## Сценарии использования

1. **Индексация.** Разработчик после пуша (или самодостаточный workflow `rag-index.yml`, спека 005) запускает `pnpm rag:index` на рабочей машине с Ollama: репозиторий обходится, документация и код нарезаются, эмбеддинги считаются локально, пишутся в `.data/knowledge.db` инкрементально.
2. **Инкрементальность.** Повторный запуск: изменён один файл, один удалён — пересчитывается только изменённый, удалённый вычищается, остальные не трогаются (достаточно по sha256 файла).
3. **Смена модели/размерности.** Модель эмбеддингов обновилась и отдаёт другую размерность: при первом несовпадении размерности индекс пересоздаётся полностью.
4. **Полная переиндексация.** `pnpm rag:index --force` — снести и пересобрать всё (например, после изменения правил чанкирования).
5. **Отладка поиска.** Разработчик запускает `pnpm rag:query "как хранится шаблон тренировки"` и видит top-k находок с файлом, заголовком и отрывком — так можно оценить качество поиска без потребителей.
6. **Помощник по проекту.** Backend (спека 004) вызывает `query()` библиотеки и использует находки как контекст для ответа с **Цитатами** (файл + заголовок).
7. **MCP-потребители.** mcp-server проксирует `search_project_docs` в `query()` (спека 002); review-CLI (спека 005) берёт top-k релевантных фрагментов знаний к диффу изменений.
8. **Прерывание.** Индексация оборвана (Ctrl+C, перезагрузка): повторный запуск доделывает без дублей и порчи индекса.

## Требования

### Функциональные (FR)

- **FR-1.** Пакет `services/knowledge` в pnpm-workspace (ADR-0001), TypeScript, публичная API — экспорты `index()` и `query()` (см. plan.md). HTTP-сервера нет: импортируется как библиотека, CLI — отдельная точка входа.
- **FR-2.** CLI-команды: `pnpm rag:index [--force]` — построение/обновление **индекса знаний**; `pnpm rag:query "<текст>" [--k 5] [--type <file_type>]` — отладочный поиск top-k с выводом `file`, `heading`, отрывка, `score`. Прогресс и итоги (файлы/чанки/пропущено) выводятся в stderr; exit-код 0 при успехе, 1 при ошибке.
- **FR-3.** Обход репозитория — ровно эти источники: `README.md`, `GLOSSARY.md`, `AGENTS.md`, `docs/**`, `specs/**`, корневые конфиги (`*.yml`, `*.yaml`, `*.json`, `*.toml`), исходники `apps/**/src/**.{ts,vue}`, `services/**/src/**/*.ts`, `package.json`.
- **FR-4.** Исключения, как в `list_files` спеки 002: `node_modules`, `dist`, `.data`, `.git`, плюс чтение `.gitignore`.
- **FR-5.** Каждый источник получает `file_type` ∈ `readme | docs | specs | adr | code | config` (карта: `README.md` → readme; `docs/adr/**` → adr (приоритет выше docs); `docs/**`, `GLOSSARY.md`, `AGENTS.md` → docs; `specs/**` → specs; исходники по FR-3 → code; корневые конфиги и `package.json` → config).
- **FR-6.** Чанкирование в **фрагменты знаний**:
  - markdown — по заголовкам; `headingPath` — склейка «Раздел > Подраздел» (от корня файла до текущего заголовка); фрагмент ≤ ~800 символов; длинный абзац режется по абзацам/предложениям;
  - код и config — файл целиком, если ≤ ~1200 символов; иначе разбиение «по крупным блокам» (функция/объект/блок верхнего уровня; эвристика по пустым строкам и отступам, без парсинга AST);
  - в каждом фрагменте сохраняются пакет/путь файла (`filePath`) и, для markdown, заголовочный путь.
- **FR-7.** Эмбеддинги — Ollama HTTP `http://localhost:11434` (переопределяется env `OLLAMA_BASE_URL`), модель `qwen3-embedding` (переопределяется env `KNOWLEDGE_EMBED_MODEL` — если модель установлена с тегом, например `qwen3-embedding:0.6b`), пакетный запрос (batch) нескольких текстов; размерность **не хардкодится** — читается из ответа при первой индексации и фиксируется в схеме таблицы.
- **FR-8.** Хранилище: `better-sqlite3` + `sqlite-vec`; путь БД из env `KNOWLEDGE_DB` (по умолчанию `.data/knowledge.db`, путь gitignored). Локальная разработка может использовать дефолт; в CI-окружении путь задаётся явно: сам workflow (спека 005, AC-8) проверяет заданность `KNOWLEDGE_DB` и быстро падает с подсказкой, чтобы индекс случайно не строился в workspace. Единственная таблица `chunks(id, file_path, file_type, heading_path, content, file_hash, embedding vec)` — `file_hash` = sha256 исходного файла, `id`/`embedding` — векторное поле sqlite-vec (схема в plan.md).
- **FR-9.** Инкрементальность по `file_hash`: файл без изменений — не пересчитывается (не перечанкуется и не гоняется через Ollama); удалённые с прошлого запуска файлы вычищаются из таблицы; `--force` — полная переиндексация (таблица сносится). Один индекс обслуживает один репозиторий (мульти-репо — вне объёма).
- **FR-10.** Поиск: `query(text, { k, type })` — эмбеддинг запроса через Ollama + векторный поиск top-k (L2). Ответ: `{ results: [{ file, heading?, excerpt (≤ 500 символов), score }], total }`; `score` — нормированная оценка близости, чем выше тем лучше; фильтр `type` — только фрагменты указанного `file_type`. Дефолт `k` библиотеки — 5.
- **FR-11.** Ошибки — осмысленные и в одно предложение: Ollama недоступна; модель не найдена («Модель <имя> не найдена — запустите `ollama pull <имя>` или задайте KNOWLEDGE_EMBED_MODEL с фактическим тегом.», где `<имя>` — фактически запрошенная модель); БД/**Индекс знаний** не построен — канонический текст «Индекс знаний не построен — запустите `pnpm rag:index`.»; размерность запроса не совпадает с размерностью индекса. Машинная классификация кодом ошибки (см. plan.md) — потребители (спеки 002/004/005) переиспользуют тексты «как есть».

### Нефункциональные (NFR)

- **NFR-1.** Производительность: полная индексация типичного репо укладывается в ~10 минут (совместимо с timeout workflow из ADR-0006); инкрементальный прогон — только изменённые файлы.
- **NFR-2.** Приватность: сетевой трафик — только локальный Ollama; содержимое/фрагменты репозитория наружу не отправляются (ADR-0005).
- **NFR-3.** Устойчивость к прерыванию: запись изменений в БД транзакционна; после обрыва остаётся консистентный индекс; повторный запуск завершает работу без дублей (один фрагмент — одна строка).
- **NFR-4.** Зависимости: `better-sqlite3`, `sqlite-vec`; CLI без фреймворков (ручной parse argv); HTTP-клиент — встроенный `fetch`. Ничего сверх обоснованного.
- **NFR-5.** Node 22 LTS + pnpm (как в CI, спека 005); пути в индексе нормализованы к POSIX-слэшам (Windows-безопасность), `file_path` — относительный от корня репо.
- **NFR-6.** Экономия токенов потребителей: `excerpt` ≤ 500 символов; API возвращает ровно поля контрактов FR-10.

## Вне объёма

- HTTP API поверх индекса (потребители импортируют библиотеку).
- Гибридный поиск (BM25/лексический), реранкинг, настраиваемые модели эмбеддингов.
- Мульти-репозиторий: один индекс = один репозиторий.
- CI-workflow индексации и review (`rag-index.yml`, `ai-review.yml`) — [спека 005](../005-ci-ai-review/).
- Генерация ответов (DeepSeek) — потребители 004/005; знания отдают только находки.
- Изменение тестируемого продукта (apps/) — только индексация кода как вход.

## Критерии приёмки

- **AC-1.** Дано: пустой `.data/`, поднят локальный Ollama с моделью `qwen3-embedding`. Когда `pnpm rag:index`. Тогда БД создана: таблица `chunks` содержит фрагменты всех источников FR-3 с заполненными `file_path`, `file_type`, `heading_path` (markdown), `file_hash`, `embedding` размерности модели (не хардкод); stderr-итог с числом файлов и чанков; exit 0.
- **AC-2.** Дано: индекс построен; 1 файл изменён, 1 удалён, остальные нет. Когда повторный `pnpm rag:index`. Тогда вывод «пересчитано N файлов» соответствует только изменённым; строки удалённого файла исчезли; сумма вызовов эмбеддингов соответствует только пересчитанным файлам (лог); exit 0.
- **AC-3.** Дано: построенный индекс. Когда `pnpm rag:index --force`. Тогда таблица пересоздаётся, все файлы переиндексируются (итог = полные числа) — в том числе при изменившейся размерности (см. AC-9).
- **AC-4.** Дано: индекс с markdown-фрагментами. Когда `pnpm rag:query "как задаются раунды и циклы"`. Тогда выведены ≤ k находок с `file`, `heading` (путь заголовков, склейка « > »), отрывком ≤ 500 символов и `score`; выход 0.
- **AC-5.** Дано: БД отсутствует. Когда вызван `query(...)` или `pnpm rag:query ...`. Тогда ошибка ровно одно предложение: «Индекс знаний не построен — запустите `pnpm rag:index`.»
- **AC-6.** Дано: индекс с фрагментами разных `file_type`. Когда `query(text, { type: 'adr' })`. Тогда все результаты `file_type = adr`.
- **AC-7.** Дано: markdown-файл с абзацем > 800 символов под заголовком. Когда индексация. Тогда фрагмент разделён на несколько (каждый ≤ ~800 символов), у каждого сохранён `headingPath` исходного заголовка.
- **AC-8.** Дано: исходник > 1200 символов. Когда индексация. Тогда файл разбит на несколько фрагментов по крупным блокам, все с одним `file_path`.
- **AC-9.** Дано: индекс размерности D1. Когда индексация с моделью, отдающей размерность D2 ≠ D1. Тогда таблица пересоздаётся под D2, переиндексация успешна, явное сообщение об изменении размерности.
- **AC-10.** Дано: env `KNOWLEDGE_DB = <путь вне репо>`. Когда `pnpm rag:index`. Тогда БД создаётся по указанному пути; по умолчанию — `.data/knowledge.db`, исключённая из git (`.gitignore`).
- **AC-11.** Дано: индексация прервана (имитация Ctrl+C между батчами). Когда повторный `pnpm rag:index`. Тогда индекс доделывается; в таблице нет дублей (одна строка на (file_path, heading_path, content)); exit 0.
